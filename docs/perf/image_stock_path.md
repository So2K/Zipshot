# Official ShareX path and timing scope

The comparison calls the unmodified ShareX 22.4.0 assemblies from the official portable build, source tag [`08bfff15e748a945944e609aca7faffbe888c7af`](https://github.com/ShareX/ShareX/tree/08bfff15e748a945944e609aca7faffbe888c7af). Its self-contained .NET runtime reports 10.0.14. The benchmark supplies its own command-line entry point; it does not start the ShareX UI or load installed user settings.

The input is a raw BGRA fixture. [The harness](../../tools/perf/image_sharex.cs) allocates a bitmap through the actual `SkiaImageHelpers.CreateBitmap`, then copies fixture bytes directly into its pixel buffer. The source bitmap is not constructed from an encoded PNG/JPEG, and is never replaced by the separate verification decoder. Alpha is premultiplied before timing because that is the stock application's native bitmap representation. The same original bitmap is passed to each measured method.

PNG/JPEG codec measurements call `TaskHelpers.SaveImageAsStream(bitmap, format, taskSettings)`. This overload matters: it passes the application's PNG settings, whereas the convenience overload uses Skia's separate default options. The actual settings captured in each `sharex-defaults.json` are PNG compression level 1, AllFilters, PNGBitDepth.Default, JPEG quality 90 and 4:2:0. A new memory stream and encoder are created for each call. Encoding uses a raw SKPixmap and does not reuse an earlier encoded file. [TaskHelpers source](https://github.com/ShareX/ShareX/blob/08bfff15e748a945944e609aca7faffbe888c7af/ShareX/TaskHelpers.cs#L484), [Skia codec implementation](https://github.com/ShareX/ShareX/blob/08bfff15e748a945944e609aca7faffbe888c7af/ShareX.HelpersLib/Helpers/SkiaImageHelpers.cs#L388).

Automatic-save measurements include **both** `TaskHelpers.PrepareImage` and `ImageData.Write` inside the timer. Bitmap allocation and fixture loading are outside it, as the comparison begins with an already captured image. The method writes the freshly encoded stream to an owned file; there is no file-resave input advantage. [Preparation source](https://github.com/ShareX/ShareX/blob/08bfff15e748a945944e609aca7faffbe888c7af/ShareX/TaskHelpers.cs#L424), [actual file write](https://github.com/ShareX/ShareX/blob/08bfff15e748a945944e609aca7faffbe888c7af/ShareX/ImageData.cs#L41).

Large opaque automatic saves can be faster than full PNG encoding plus JPEG encoding because ShareX passes the JPEG byte threshold into a `SizeLimitedWStream`. Once a write would exceed that threshold, the stream returns failure and PNG encoding stops; preparation then encodes JPEG. It does not finish PNG rows that will be discarded. The standalone PNG codec measurement instead has an unlimited output stream. Zipshot's baseline WIC save encoded the entire PNG before making this decision, which is a real algorithmic difference rather than cached encoded input. [Bounded stream and early termination](https://github.com/ShareX/ShareX/blob/08bfff15e748a945944e609aca7faffbe888c7af/ShareX.HelpersLib/Helpers/SkiaImageHelpers.cs#L423).

Default thresholds are different units: ShareX uses 2048 decimal KB, Zipshot uses 2048 binary KiB. The labelled matched ShareX run uses 2,048,000 bytes. Stock automatic save may flatten alpha to JPEG, while Zipshot retains alpha PNG, so those alpha save rows are not equal-output comparisons. File I/O measures normal cached writes, not durable-storage flush latency. No full application or UI latency is inferred from these image-API measurements.
